Agent platform pipelines

Four parts of the agent platform used to be deployed by hand. All four now deploy from CI, on both environments.

Verified against AWS · 21 October 2026

What deploys, and when

WorkflowDeploysTriggered by
agent-egress-proxySquid allowlist image → proxy servicepush touching egress/**
agent-platformPlatform stack: Lambda, state machines, Scheduler, CodeBuildpush touching platform/**
agent-control-planeControl-plane image and database migrationspush touching agent-control-plane/**
agent-secrets-rollNothing new — restarts tasks so they re-read secretsmanual dispatch only

Schema lands before the code

Why a ledger, not idempotent SQL. The migration SQL is not re-runnable — one file has 32 DDL statements with only four IF NOT EXISTS guards. A ledger table records what has run, and only files absent from it execute. That is what makes a push-triggered migration safe.

The branch picks the environment

Consequence. A migration applied from nonprod is applied for dev too. Images and stacks can be staged nonprod-first; migrations cannot.

Testing it

Everything in the first group runs without AWS credentials, so it also runs on a pull request.

# 40 allowlist assertions, no container needed
bash test_squid_config.sh

# platform suite; db tests skip unless a test DSN is set
uv sync --locked && uv run pytest -q

# the Lambda zip builds with no credentials at all
uv run python deploy.py --package-only

# what the migrate job would do — read-only
python migrations/runner.py status --secret <env-secret>

actionlint .github/workflows/agent-*.yml

Then, in order:

  1. Push to nonprod, confirm green, verify in AWS.
  2. Push to dev, confirm green, verify in AWS.
  3. Dispatch the secrets roll per environment when a secret value changed.

Verify the deploy, not the workflow

A green run is not proof. Check the thing it claims to have changed:

PipelineWhat actually proves it
Egress proxyService runs CI's image tag, and the docs endpoint that reaches PyPI through the proxy returns 200
Platform stackNot the stack status — a no-op update looks identical. The Lambda's LastModified is what shows code moved
Migrationsmigrate's start time precedes deploy's in the run's job list
Secrets rollTask definition revision unchanged while the deployment is new — that is what proves a restart shipped no code

Six things that cost real time

#SymptomCause
1ProfileNotFoundDeploy scripts defaulted to a laptop-only AWS profile. CI has none — credentials arrive in the environment
2429 Data limit exceededAnonymous public-registry pulls are capped. The base image failed before a layer built; authenticate to the public registry too
3Opaque sts errorA job declaring an environment: changes the OIDC subject from ref:… to environment:…. Trust policies listing only branch refs reject it
4Fails on dev, passes on nonprodThe gateway URL is read from the hosting stack's output, and only nonprod has a fallback. Nonprod passing does not prove dev will
5404 … not found on the default branchA workflow_dispatch workflow must exist on the default branch or it cannot be dispatched at all. Push triggers have no such rule
6No review ever happensNo deployment environment has protection rules, so nothing is reviewer-gated — even where workflow comments imply otherwise

Gotcha 4 is the argument for staging nonprod-first, and for its limit: one environment passing is evidence, not proof.
